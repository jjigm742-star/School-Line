# 《스쿨라인》 1.9.1 — 랜덤 경쟁전 + 버전별 통계 + FPS 최적화

## 공식 버전 및 데이터 보존

- 게임 버전 / npm: **1.9.1**; 캐릭터 밸런스: **1.9**; 경쟁전 통계 시리즈: **1.9**; 26종 로스터 동일.
- 업로드된 1.9 portrait cropfix를 기준으로, 사용자 요청에 따라 기존 1.9 FPS 최적화(정적 맵 오프스크린 캐시, HUD DOM 갱신 간소화, 색상표 재사용) 및 관리자 PIN 변경을 함께 반영했다.
- 원본 경기 기록, 통계 테이블, 캐릭터 수치, 드래프트, 전투 판정, 점유/승리 조건은 수정하지 않는다.
- **운영 PostgreSQL 및 호스팅 서버에는 접속하거나 배포하지 않았다.** ZIP에 `data/` 및 실제 계정·경기 데이터를 포함하지 않는다.
- PostgreSQL은 그대로 영구 저장소. 기존 `school_line_matches`의 `record` JSONB에 추가 필드를 넣으므로 DB 스키마 변경 없이 기존 `match_id` 기본키와 `ON CONFLICT DO NOTHING` 중복 방지 기능을 재사용한다.

## 경쟁전 랜덤 매칭

- 메인 화면 「경쟁전 매칭」 버튼으로 계정 PIN 인증 후 독립적인 FIFO 대기열에 등록. 기존 방 만들기/방 목록/수동 경쟁전 진입 기능 유지.
- 먼저 신청한 8명에게 참가 확인 절차 제공. 기본 제한시간 **20초** (`SCHOOL_LINE_QUEUE_CONFIRM_MS`, 최소 1000ms). 거절 또는 미확인 참가자는 제거하고 더 오래 기다린 학생부터 보충. 기존 확인 참가자의 우선 순번 및 확인 상태는 유지.
- 통신 연결 끊김은 기본 **30초** (`SCHOOL_LINE_QUEUE_RECONNECT_MS`, 최소 1000ms) 유예. 같은 계정/PIN으로 재접속하면 원래 신청 순서로 복원하며, 그룹 확인 중 돌아온 학생에게는 새 20초 확인 기회를 제공. 유예 시간 동안 뒤 신청자가 해당 순서를 추월하지 못하도록 대기열 순서를 보존한다.
- 계정 중복 신청·타 기기 중복 등록·대기 중 다른 방 입장을 서버가 차단. 대기 취소는 즉시 제거. 서버의 단일 이벤트 루프에서 순서대로 상태를 갱신한다.
- 8명 모두 확인하면 `crypto.randomInt` 기반 Fisher-Yates로 무작위로 섞고 A/B 각 4명 배정. 전적·승률·과거 팀 구성은 일절 참조하지 않는다. 방 생성 후 수동 팀 변경·수동 입장·모드 변경·매치 재시작 차단. 기존 밴픽 단계 `startCompetitiveDraft()`로 연결.
- 기존 최대 5개 방 동시 실행을 존중. 16명 이상이면 방 여유가 있는 한 8명씩 병렬 경기 생성. 방이 가득 차 있으면 확인 완료한 그룹이 우선권을 유지하며 빈 방을 기다림.
- 경기 후 자동 재매칭 없음. 종료 결과 화면에서 「방 나가기」를 누르고 메인 화면에서 다시 신청한다. 진행 중인 경기의 기존 재접속 로직을 그대로 사용.
- 서버 프로세스 재시작 시 **진행 중이던 대기열은 복구되지 않음**(인메모리 큐). 재시작 이후 다시 신청 필요.

## 통계 필터 및 보존

경기 원본 예: `gameVersion: "1.9.1"`, `balanceVersion: "1.9"`, `statsVersion: "1.9"`, `matchMode: "competitive"`, `matchmakingMode: "random_queue"`. 수동 방 신규 기록에는 `matchmakingMode: "manual_room"`이 붙는다. 기존 기록에 매칭 방식을 소급 덮어쓰지 않는다.

통계 선택창에서 **1.9 단독** (`gameVersion=1.9`), **1.9.1 단독** (`gameVersion=1.9.1`), **1.9 통합** (`두 게임 버전의 원본 합산`)이 각각 전체 캐릭터·플레이어·밴픽·시너지·매치업·피해·치유 등의 지표에 적용된다. 합산 승률은 실제 승패 총합으로 계산. JSON 백업에는 변경 없는 과거 원본과 신규 필드가 포함된다. 원본에 `gameVersion`이 없는 미확인 과거 기록은 **추측해서 버전별 통계로 배정하지 않음**. 해당 원본은 전체 백업에 보존된다.

> **중요:** 1.9 통합 통계에는 같은 밸런스를 사용한 *수동 편성 경기*와 *무작위 편성 경기*가 섞일 수 있으며, 두 환경의 승률·픽률을 비교할 때 이를 고려해야 한다.

## 배포 주의 및 검증 한계

- 배포 전 운영 PostgreSQL 및 서버 환경을 별도 백업한 후 스테이징에서 계정/PIN·관리자 잠금·8인 경쟁전·3분 경기 종료와 실제 DB 쓰기를 확인.
- 실제 운영 PostgreSQL 연결을 통한 경기 결과 영속 저장·가져오기, 모바일 기기 8대에서의 성능·와이파이 연결 지터는 이번 로컬 검사에 포함되지 않는다.
- 서버를 여러 **프로세스 또는 인스턴스**로 수평 확장한 경우 현재 인메모리 큐는 프로세스별로 독립됨. 단일 스쿨라인 서버 인스턴스 기준 설계이며, 다중 인스턴스 공유 큐는 별도 Redis/DB 트랜잭션 설계가 필요하다.
- 4자리 관리자 PIN은 이전 1.9 성능 패치에서 합의한 값으로 해시 형태만 서버 소스에 저장됨; 학생용 개별 PIN은 변경하지 않음.
